# 四个最常见的坑：机理与修法

这四个坑覆盖了 DEM 处理中绝大多数"结果看起来能用、其实已经错了"的情况。
`verify_output.py` 会把第 1、2、4 项自动查出来。

## 坑一：边界外一圈黑边

**现象**：预览图边界外有一圈纯黑；或高程直方图里出现大量 0 值。

**机理**：原始瓦片没有声明 nodata，掩膜裁切后边界外被填成 0。
0 在高程里是**合法值**（如沿海洼地），不是空值——它不透明、参与统计、参与插值，
于是变成一圈深度 0 m 的"环形洼地"，汇水、坡度、渲染全部被污染。

**修法**：掩膜时显式写 NaN；输出 RGBA 预览时把 nodata 写成 alpha=0。
本技能 `clip_by_boundary.py` 默认如此；下游软件不支持 NaN 时用 `--nodata -9999`。

## 坑二：瓦片拼缝细黑线

**现象**：跨瓦片区域合成图上有规则的直线黑线/条纹。

**机理**：合并 1° 瓦片时未显式传 nodata，边缘留了 -32768 这类哨兵值。

**修法**：`merge` 显式 `nodata=-32768`，再 FillNodata 补洞（`--fill`）。

## 坑三：整幅图偏移几百米

**现象**：DEM 和影像/边界叠不上，整体差半个街区。

**机理**：国内互联网地图的行政边界（高德、阿里 DataV）是 **GCJ-02 加密坐标**，
而 Copernicus 影像/DEM 是 **WGS84**。直接叠，偏移 100–700 m，且随地区变化。

**修法**：裁切前把边界迭代反解回 WGS84（本技能默认执行，误差 < 1 m，
`--no-convert` 才跳过）。反过来提醒：**自己找的 WGS84 边界别忘了这次转换是多余的**，
用 `--no-convert`。

## 坑四：高程差几米，符号还可能反

**现象**：和 GPS 实测点比对，系统性差零点几到几米。

**机理**：GLO-30 是 **EGM2008 正高**；国内工程常用 **1985 国家高程基准**；
GPS 输出的通常是 **WGS84 椭球高**。三者两两不同，中国大陆没有公开的官方
EGM2008→1985 偏移格网，差异通常 ±0.5 m 内但随区域变化。

**修法**：诚实承认没有权威格网。`datum_convert.py` 提供 EGM2008↔椭球高的显式换算
（`--to ellipsoidal` / `--to orthometric`，注意 `--multiplier` 符号）；
要归算到 1985 基准，用本区实测水准点填常数偏移校准。
**用于出图不用管；用于土方量计算必须校准。**

## 附加：DSM vs DTM

GLO-30 是 DSM（表面模型），含树冠和建筑。城区高程被整体抬高
（作者实测参考：合肥城区均值 +34 m）。拿它算城区内涝、建筑周边汇水会出错；
拿它算山区坡度、选线走廊、流域趋势没问题。目前没有免费的全球 30 m DTM，
需要裸地形时要么滤除（有误差），要么走商用/测绘数据。
